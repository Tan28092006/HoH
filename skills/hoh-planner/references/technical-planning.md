# Technical planning with workflow

Use the installed `workflow` for technical planning. Generated Planner prompts
explicitly request it; bootstrap routes the required practice skill. Neither
routing, loading a skill nor declaring a manifest proves that tools ran. Do not
enable global hooks, change activation policy or claim new server enforcement.

## Applicable stages and authority

Apply workflow preparation, acceptance criteria, prior-review research, context
mapping and design, then review the plan against the evidence. Implementation,
candidate QA, integration and deployment stages are not applicable to the Planner
role. Do not implement code, issue QA verdicts, merge or deploy. Follow existing
role/project/auth, reconciliation and current-context guards.

Keep preparation state in authorized task-local storage. Do not write a read-only
checkout to initialize workflow notes or create another authoritative ticket
tracker. Persist the resulting technical findings through existing Planner
decisions, context and ticket contracts.

## Research before a technical release or revision

1. Bind the question to the authorized repository/worktree root, target/base and
   current revision, relevant dirty/generated inputs and the current ticket/spec
   references. Distinguish service installation, repository main and candidate
   source. A remote MCP identity does not grant local filesystem or Git access.
2. Read actual source definitions and relevant specification, interfaces/schema,
   configuration, guards and tests/assertions. Trace input construction, callers,
   consumers and affected writes. Do not infer behavior from names or fixture
   values. Identify both expected results and forbidden effects.
3. Discover installed graph tools and their actual schemas/help. Use the installed
   GitNexus CLI when MCP is unavailable, as workflow directs. Bind each query,
   symbol context and upstream impact result to the right root, indexed revision,
   relevant source state and output reference. Do not use an ambiguous alias or
   another checkout's index. Verify dirty/new/generated coverage; a green commit
   status alone is insufficient.
4. Inspect the bodies and callers returned by the graph. Cross-check dynamic
   dispatch/mixins, string registration, generated assets and other uncovered
   edges with direct search and contract evidence. Empty callers, truncated
   results, UNKNOWN or unsupported scope do not prove safety. Record missing
   tools, stale/missing indexes and uncovered edges as unresolved, not passed.
   Refresh relevant analysis only within authorization when source coverage
   changes; do not install tools or rewrite instructions to manufacture a pass.
5. Translate findings into a concrete plan: entrypoint/interface changes,
   prerequisite ticket dependencies, repository-relative write scope, sequencing
   or concurrency constraints, acceptance/preservation criteria and required
   validation scenarios/capabilities. A source-call edge is not itself a ticket
   dependency or evidence that prerequisite work is DONE. Use existing dependency
   and lifecycle tools for those facts.

Record a concise evidence map with the question, root/revision/source identity,
inspected definition/caller/contract/test, graph command/output and limits, then
the dependency/scope/validation decision it supports. Keep required missing
evidence unresolved for the affected technical release/revision; continue
independent authorized planning. Do not add a project-wide barrier or wait for
routine Planner advice where the existing lifecycle does not require it.

## Freshness without repeated idle work

Reuse relevant unchanged research. Reassess when source/spec/contracts,
dependencies, interfaces, relevant dirty inputs or query coverage change. An
idle event, heartbeat, delivery acknowledgement or unchanged test run does not
require full reindexing, implementation checks or another full suite. Preserve
the existing asynchronous control cycle and refresh current server context
before consequential writes. A technical blocker belongs in existing planning
records; do not create a new protocol, schema, executor or verification claim.
